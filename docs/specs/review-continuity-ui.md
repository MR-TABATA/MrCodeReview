# 複数回レビューの「つなぎ」UI

- 作成日: 2026-11-17
- 状態: 下書き

## 目的
今のUIは、レビュー 1 回ごとに独立した 1on1 の前提で、前回のレビューを受けた今回のレビュー、という流れが見えない。
前回と今回がつながって見えるUIに改善する。

## 決めたこと
- A〜D の 4 つを、すべてやる（1 つの流れとして見せるには、4 つが揃う必要がある）。
  - なぜ: 「全部やんないと意味なくない？」という本人の判断。A・B だけでは 1 つの結果画面で完結し、履歴からたどれず、実行前にも「続き」が見えない。
- **A. 結果の先頭に「前回 → 今回」の帯を出す。**
  - 前回の日時・件数と、今回の「継続 / 解消 / 新規」の件数を出す。
  - 押すとその種類で絞り込める。前回のレビューへ飛ぶリンクを付ける。
- **B. 指摘カードに、前回との関係の印を付ける。**
  - 「新規」「継続（前回 #3）」。リンクで前回の指摘へ飛べる。
- **C. 履歴を「観点 × リポジトリ」の流れでたどれるようにする。**
  - 各行に前回との増減（＋2 −3）を出し、線でつなぐ。
- **D. 実行バーに、前回があるときだけ「前回の続きから（日時・件数）」のワンボタンを出す。**
- **確定（2026-11-18、タスク 1 のあと）**:
  - 「前回」は、**観点ごと**（同じリポジトリ・同じ観点の直前。`store::recent_ok` が土台）に統一する。D のボタンも「この観点の前回」を指す。既存の比較元「前回のレビューの続き」（`store::last_review`、観点を問わない）は別物として残し、画面の文言で区別する。
  - `Carry` は、未仕分けの指摘にも付けて「継続」を判定する。ただし「引き継ぎました」の表示（`carryNote`）と仕分け履歴の `carry` 記録は、仕分け済みのときだけ。
- 「前回」の定義を 1 か所に決め、A〜D はすべてそれを参照する。定義は、同じリポジトリ・同じ観点で、成功した直前のレビュー。
  - なぜ: （会話に理由なし。方針として提示し、本人が了承）
- 「新規／継続／解消」を意味のあるものにするため、`Fate`（前回の指摘が今回どうなったか）を、前回の全指摘に広げる。今は「対応」「待ち」だけが対象。Rust 側（エンジン）の変更とテストが要る。
  - なぜ: 今の対象だと、今回新しく出た指摘と、前回からの全体の増減が見えないため。
- 実装は A → B → D → C の順で、各段階でローカルに起動して本人に見せる。
  - なぜ: （会話に理由なし。方針として提示し、本人が了承）
- C のときに、右サイドバーの窮屈さ（保留中の項目）も一緒に見直す。
  - なぜ: 履歴の行に増減や線を足すと、右サイドバーがさらに窮屈になり、保留中の課題とぶつかるため。

## 受け入れ基準
- 同じリポジトリ・同じ観点のレビューを 2 回続けて実行すると、2 回目の結果の先頭に、前回の日時・件数と、継続・解消・新規の件数が出る（確かめ方: 架空のリポジトリ `npm run demo-repo` で 2 回走らせ、ローカルで起動して目視）。
- 前回の全指摘について、継続・解消のどちらかが判定される。「対応」「待ち」以外も対象になる（確かめ方: `cargo test --workspace` に、未仕分けの指摘のケースを足す）。
- 前回が無いとき（初回）は、帯・印・「前回の続きから」ボタンを出さない（確かめ方: 初回の実行をローカルで目視）。
- 指摘カードから、前回の指摘へ飛べる（確かめ方: ローカルで目視）。
- 履歴の行に、前回との増減が出る（確かめ方: ローカルで目視）。
- 既存の試験が通る（確かめ方: `cargo test --workspace`、`cd app && npm test`、`npm run typecheck`）。

## 未決事項
- （解決）`Carry` が「未仕分け」の指摘にも付くか → 付かなかった（`carry.rs` の候補が `state != new`）。上の「確定」のとおり、付ける方針に変えた。
- ほぼ一致（トークン一致率 90% 以上）でも、未仕分けの指摘を「継続」と判定してよいか（実装では「待ち」「無視」と同じ扱いにした。誤判定の様子は、A の段階で見て決める）。
- 前回の指摘が 0 件のとき、`fates` が空になり、「前回のレビューの id・日時」が記録から取れない。A の帯のために、`ReviewRecord` へ前回の id を足すか、別の取り方にするか。
- 「前回」の定義（同じリポジトリ・同じ観点で、成功した直前）が、複数の観点を同時に走らせた場合などにも成り立つか。
- 「継続」「解消」の判定の根拠（今の `Fate` は、引用した行がコードに残っているかを根拠にした推定）を、全指摘に広げたときも同じでよいか。
- 前回が、別の比較元（例: 「前回のレビューの続き」ではなく全体）で走っていた場合の、継続・解消の扱い。
- A の「絞り込み」の具体的な見せ方（既存の指摘の並び・フィルタとの関係）。
- C の履歴の「線」の具体的な見た目と、右サイドバーの窮屈さの解消方法。
- 新しい文言の英語版（`locales.ts` は日英あり）の扱い。
- 画面の見た目は、各段階で本人に見せて決める（事前に固めていない）。
