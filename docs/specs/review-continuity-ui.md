# 複数回レビューの「つなぎ」UI

- 作成日: 2026-11-17
- 更新日: 2026-11-18
- 状態: 実装中（A・B・D と、レビューの連番は実装済み。C は未着手）

## 目的
今のUIは、レビュー 1 回ごとに独立した 1on1 の前提で、前回のレビューを受けた今回のレビュー、という流れが見えない。
前回と今回がつながって見えるUIに改善する。

## 決めたこと

### 全体
- A〜D の 4 つを、すべてやる（1 つの流れとして見せるには、4 つが揃う必要がある）。
  - なぜ: 「全部やんないと意味なくない？」という本人の判断。A・B だけでは 1 つの結果画面で完結し、履歴からたどれず、実行前にも「続き」が見えない。
- 実装は A → B → D → C の順で、各段階でローカルに起動して本人に見せる。
  - なぜ: （会話に理由なし。方針として提示し、本人が了承）
- C のときに、右サイドバーの窮屈さ（保留中の項目）も一緒に見直す。
  - なぜ: 履歴の行に増減や線を足すと、右サイドバーがさらに窮屈になり、保留中の課題とぶつかるため。

### 「前回」の定義（1 か所）
- 「前回」は、**同じリポジトリ・同じ観点で、成功した直前のレビュー**。A〜D はすべてこれを参照する。実装は `store::recent_ok` の先頭、記録は `store::PreviousRef`（`ReviewRecord.previous`）。
- 実行した時点の「前回」を、記録に残す（あとで新しいレビューが増えても、過去の記録の「前回」は変わらない）。
- 観点を問わない「リポジトリの直近」（`store::last_review`）は、比較元「前回のレビューの続き」のためのもので、別物として残す。
  - なぜ: 本人が「観点ごとに統一」を選んだ。

### 前回の指摘の行方（`Fate`）と引き継ぎ（`Carry`）
- `Fate` は、前回の**全指摘**（仕分けを問わない）が対象。以前は「対応」「待ち」だけだった。
  - なぜ: 今回新しく出た指摘と、前回からの全体の増減が見えるようにするため。
- `Carry` は、前回の「未仕分け」の指摘にも付ける（同じ指摘かどうかの判定に使う）。ただし、`Carry.state` が "new" のときは、引き継ぐ仕分けは無い。「↺ 引き継ぎ」の印・「引き継ぎました」の表示・仕分け履歴の `carry` 記録は、仕分け済みのときだけ。
- 「継続」は前回の指摘と結びついた今回の指摘、「新規」はそれ以外の今回の指摘、「解消」は前回の指摘のうち引用の行がコードから消えたもの、「再指摘なし・不明」は前回の指摘のうち今回の指摘と結びつかず「解消」とも言えないもの。判定は `app/src/continuity.ts`（帯・印・絞り込みが同じ関数を使う）。

### A. 結果の先頭の「前回 → 今回」の帯
- 表示: 「前回 潜在バグ_2（指摘 2 件）→ 今回 潜在バグ_3（指摘 1 件）」。前回の名前を押すと、前回のレビューへ移る。**日時は、帯には出さない**（名前で探せるため。マウスを載せたときだけ出る）。
  - なぜ: 本人が「日時はいらん」と判断した。
- 「継続／解消／新規／再指摘なし・不明」の件数のボタン。押すとその種類だけに絞る（もう一度押すと外す。0 件は押せない）。「解消」「再指摘なし・不明」を選ぶと、今回の指摘は出さず、前回の指摘の行方の一覧だけを出す。
- 同じ観点の流れの 1 行（「潜在バグ の流れ 1（0 件） → 2（2 件） → 3（1 件） → [4（0 件）]」）。今のレビューは `[ ]`、ほかは押すと開く。履歴にある分だけ（消した番号は欠ける）。長いときは今の近くの 8 件。2 件に満たなければ出さない。数字の前の `_` は付けない。
  - なぜ: 本人が「ここには 2 と 1 は表示されない？」と聞き、「1 で入れてみて」「アンダースコアは不要」と決めた。
- 下の「前回のレビューからの変化」の見出しは、前回の名前を入れる（「潜在バグ_3 からの変化」）。
- 前回が無い（初回）ときは、帯を出さない。

### B. 指摘カードの印
- 前回があるレビューで、各カードの小さな印の先頭に、「新規」または「継続（前回 #N）」を出す。継続は、押すと前回のレビューのその指摘が開いた状態で移る。
- 初回、および差分に重ねる小さなカードには出さない。

### D. 実行バーの「前回の続きから」
- 実行ボタンの**左隣**、同じ高さ、1 行、観点 2 つ分の幅。文言は「前回の続きから（潜在バグ_4・1 件）」。押すと、見る範囲を「その観点の前回のレビュー時点のコミット以降」にして、そのまま実行する。
  - なぜ: 本人が配置を指定した（「実行ボタンの左横。天地は同じにする。1 行にする。観点 2 つ分」）。
- 出す条件:
  - 観点を **1 つだけ**選んでいるとき（観点ごとに前回の比較元が違うため）。
  - **前回の指摘が 1 件以上**あるとき。0 件のときは出さない（本人が「前回 0 件で続きからは、うーん」）。
  - 見る範囲が、すでに前回の続きでないとき。
  - 前回のコミットが、いまの履歴の祖先にあるとき（rebase・amend・別ブランチのときは出さない。黙って全体を送らない）。失敗したレビューは、前回にならない。
- 比較元は、その観点自身の前回の HEAD のハッシュ。別の観点のレビューを挟んでも動かない。
- 読み込みの扱い: 観点を変えたら前の材料は捨てる／古い読み込みの結果は捨てる／押した時点で材料の観点が今の選択と同じか確かめる／読めなかったときは、「前回が無い」と同じ見え方にせず、理由を実行バーの注記に出す。

### レビューの連番（追加）
- 名前は「**潜在バグ_1**」（観点の名前 + `_` + 連番、0 埋めなし）。リポジトリ × 観点ごとに数える（同じアプリでも、潜在バグと例外処理は別に数える）。出す場所: 履歴の行、結果の見出し、帯、変化の見出し。
  - なぜ: 本人が「12:23 とかを探さなきゃなので」番号を求め、「潜在バグ_1 でいんじゃね？アプリごとに連番にするよね」と決めた。0 埋めは、意見を聞かれ、本人は変えなかった（私の意見: 画面の並びは時刻順なので、0 埋めは要らない）。
- 番号は、実行して記録に残すときに決めて保存する（`store::append_numbered`）。履歴を消しても、他の番号は変わらず、**最新を消しても、同じ番号を使い回さない**（最終値を別の表 `review_seq` に持つ）。
- 番号の無い古い記録には、データベースを開いたとき、一度だけ、実行時刻の順に番号を振る。
- データベースの版を 3 → 4 に上げる（`reviews.seq` 列・`review_seq` 表）。移行（列の追加・連番・版の更新）は、1 つのトランザクション。**この版で開いたデータは、古い版では開けない**（リリース前に、案内が必要）。
- 連番の最終値を書けなくても、履歴の保存は巻き込まない（警告のみ）。

## やらないこと
- 本人の実データを開いての確認はしない（実装段階でも、架空のデータ・隔離した環境で見せる）。
  - なぜ: 本人の全般的な方針（実データは勝手に開かない）。
- 「CLI に渡す」まわりの手作業の自動化。ロードマップの項目 3 に記録し、自動化をまとめて検討するときに決める（本人: 「今は手動だらけなので」）。

## 受け入れ基準
- 同じリポジトリ・同じ観点のレビューを 2 回続けて実行すると、2 回目の結果の先頭に、前回の名前・件数と、継続・解消・新規の件数が出る。（確認済み: 本人が実機で、帯の「解消 2・新規 1」「再指摘なし」を見た。「継続」は、まだ出ていない）
- 前回の全指摘について、行方が判定される。「対応」「待ち」以外も対象になる。（確認済み: `cargo test --workspace`）
- 前回が無いとき（初回）は、帯・印・「前回の続きから」を出さない。ボタンは、前回が 0 件でも出さない。（確認済み: 判定の関数のテストと、`continue_info` のテスト。**初回の画面は、本人はまだ見ていない**）
- 指摘カードから、前回の指摘へ飛べる。（**実機で未確認**。「継続」の指摘が出る場面が、まだ無い）
- 履歴の行に、前回との増減が出る。（**C が未着手**）
- 番号は、履歴を消しても、他の番号が変わらず、使い回されない。（確認済み: `store.rs` のテスト）
- 古いデータベースを開くと、番号が一度だけ振られ、失敗したら元に戻る。（確認済み: `db.rs` のテスト）
- 既存の試験が通る。（確認済み 2026-11-18: `cargo test --workspace`、`cd app && npm test`、`npm run typecheck`）

## 未決事項
- 「ほぼ一致」（トークン一致率 90% 以上）でも、未仕分けの指摘を「継続」と判定してよいか（実装では「待ち」「無視」と同じ扱い。誤判定の様子は、まだ見ていない）。
- 「継続」「解消」の判定の根拠（引用した行がコードに残っているかの推定）で足りるか。実機では、指摘の行はそのまま残るのに別の方法で直した場合に「再指摘なし」になる、という見え方が出た（例: 直した指摘の引用の行が、そのまま残る）。
- 前回が、別の見る範囲（例: 前回は「直近のコミット」、今回は「未コミットの変更」）で走っていた場合の、継続・解消の扱い。
- 失敗した実行にも番号を振っている（履歴に出るものは、歯抜けにしないため）。本人の明示の確認は、まだ無い。
- 連番の振り直しの起点を、「履歴の最大値」だけでなく「記録してある最終値」とも比べるか（手作業でデータベースを統合したときの、狭い穴。コードの経路では起こらない）。
- 帯の下の注意書きと「前回のレビューからの変化」の末尾の注意書きが、ほぼ同じ文で重なっている。まとめ方（B・C の段階で整理する予定）。
- 帯・流れの行・前回の続きから・変化の見出しの文言が、日本語の直書き（「新規」「継続」の印だけが `locales.ts` に日英ある）。英語版の扱い。
- 「前回の続きから」は、観点を 1 つだけ選んでいるときだけ出す（観点ごとに比較元が違うため、私が決めた）。複数の観点を選んでいるときの出し方は、決めていない。
- 既存の見る範囲の「前回のレビューの続き」（観点を問わない）と、D の「前回の続きから」（観点ごと）の関係。画面の文言で区別するか、統合するか。
- 前回のレビューが履歴から削除されているとき、帯の前回の名前（リンク）の扱い。
- 引き渡しファイル・レポートに、レビューの番号を併記するか（識別子 `mrcr:…` は、そのまま）。
- 「複数のコミットをまたぐ長く残っている指摘」（_1 から出ていて、_2・_3 でも出る指摘）を、どう見せるか（今の判定は、直前の 1 つとの比較だけ）。
- C の履歴の「線」の具体的な見た目と、右サイドバーの窮屈さの解消方法。
- 画面の見た目は、各段階で本人に見せて決める（事前に固めていない）。
- MrkCodeReview（`mrcr-core` を直接読む別リポジトリ）が、`ReviewRecord` の新しい項目（`previous`・`seq`）に追従する必要がある。追従の 2 行は、別リポジトリに、未コミットで入っている。
